# Complex Example: Satek Procurement

This guide walks through **Satek**, a real-world procurement and warehouse management system built with Lesan. It is the largest and most complete Lesan project you can study: **30 models**, a multi-step approval workflow, role-based access control with feature flags, warehouse inventory tracking, tenders, budget encumbrance, and full-text search across almost every list endpoint.

Unlike the focused snippets in the [Advanced Guides](/docs/advanced/client-projections), this page shows how those pieces fit together in one coherent application. We keep the code faithful to the real project (imports are adapted from `lesan` to `@hemedani/lesan` for consistency with the rest of this documentation).

:::info Source
The project is open source. The excerpts here are trimmed to the interesting parts; the full code contains much more business logic per act.
:::

## Domain Overview

Satek is a hospital procurement platform. The core document is the **purchasing request (PR)**: a unit requests items, the request flows through configurable approval steps, a tender is created and awarded, goods are received into a warehouse, inventory is tracked per warehouse, and budget lines are encumbered along the way.

```text
unit ──requests──> purchasingRequest ──flows through──> process (steps)
                         │                                      │
                         ├── requester (user)                   ├── stepApproval
                         ├── wareModel / ware / stuff            └── history[]
                         ├── store / wareType / wareClass / wareGroup
                         ├── tender (offers) ──awarded──> paymentOrder
                         ├── budgetLine ──encumbers──> budgetAllocation / budgetEncumbrance
                         └── goodsReceipt ──moves──> inventory / stockMovement / consumption
```

## Project Layout

Satek organizes a Lesan app into four directories, one file per model and one folder per act:

```text
back/
├── mod.ts                      # entry: lesan(), setDb, model registration, runServer
├── models/
│   ├── mod.ts                  # barrel that re-exports every model factory
│   ├── user.ts                 # one file per model: pure fields + relations + factory
│   ├── purchasingRequest.ts
│   ├── excludes.ts             # shared field-exclusion lists for relations
│   ├── featureConstants.ts     # feature-enum array used by feature flags
│   └── ...
├── src/
│   ├── mod.ts                  # functionsSetup(): calls every act's *Setup()
│   ├── user/
│   │   ├── mod.ts              # userSetup(): registers all user acts
│   │   ├── login/
│   │   │   ├── mod.ts          # setAct({ schema, actName, fn, validator, preAct })
│   │   │   ├── loginUser.fn.ts # the ActFn implementation
│   │   │   └── loginUser.val.ts# the superstruct validator
│   │   └── ...
│   └── purchasingRequest/
│       ├── add/ gets/ update/ remove/ count/ ...
└── utils/
    ├── mod.ts                  # barrel (@lib alias)
    ├── context.ts              # MyContext extends LesanContenxt
    ├── setToken.ts setUser.ts  # auth preAct hooks
    ├── grantAccess.ts          # role/feature/scope preAct hook
    ├── pagination.ts           # shared { page, limit, skip } superstruct
    ├── createUpdateAt.ts       # shared { createdAt, updatedAt } pure fields
    └── throwError.ts
```

The `mod.ts` entry wires everything together:

```ts
import { lesan, MongoClient } from "@hemedani/lesan";
import { users, purchasingRequests, ... } from "@model"; // path-alias to ./models/mod.ts
import { functionsSetup } from "./src/mod.ts";

export const coreApp = lesan();

const client = await new MongoClient(Deno.env.get("MONGO_URI") || "mongodb://127.0.0.1:27017/").connect();
coreApp.odm.setDb(client.db("lesanSatek"));

export const user = users();               // registering a model returns the ODM handle
export const purchasingRequest = purchasingRequests();
// ... one exported handle per model

export const { setAct, setService, getAtcsWithServices } = coreApp.acts;
export const { selectStruct, getSchemas } = coreApp.schemas;

functionsSetup();                          // registers every act

coreApp.runServer({
  port: 1370,
  typeGeneration: true,
  playground: true,
  staticPath: ["/uploads"],                // serve uploaded files
  cors: ["http://localhost:3000", "http://localhost:3005"],
});
```

:::tip Model registration order matters
Each `newModel` call registers one schema and then rebuilds the inverse (`relatedRelations`) map for *every* schema. Satek keeps all registrations together in `mod.ts` in dependency order, then re-exports the handles so any act in `src/` can import its model from `mod.ts`.
:::

## The Model Layer

### `newModel` with indexes and excludes

Two model-level options you have seen in snippets but rarely combined: `createIndex` and `excludes`. Satek uses them on the `user` model — a unique index on `email` (created at registration) and a model-level `excludes` so the password is never included in a pure projection:

```ts
export const users = () =>
  coreApp.odm.newModel("user", user_pure, user_relations, {
    createIndex: {
      indexSpec: { email: 1 },
      options: { unique: true },
    },
    excludes: ["password"],
  });
```

For a compound index on a model registered *without* one, Satek grabs the raw collection and creates it after `setDb`:

```ts
export const createInventoryIndex = async () => {
  const collection = coreApp.odm.getCollection("inventory");
  try {
    await collection.createIndex({ unit: 1, "ware._id": 1 }, { unique: true });
  } catch (error) {
    console.error("compound index exists already", (error as Error).message);
  }
};
```

### Full-text indexes

Almost every `gets` act supports a `search` field backed by a MongoDB **text index**. Some are declared in `newModel`:

```ts
export const purchasingRequests = () =>
  coreApp.odm.newModel(
    "purchasingRequest",
    purchasingRequest_pure,
    purchasingRequest_relations,
    { createIndex: { indexSpec: { title: "text", description: "text" } } },
  );
```

Others are created manually after registration:

```ts
export const createUserTextIndex = async () => {
  const collection = coreApp.odm.getCollection("user");
  await collection.createIndex({ first_name: "text", last_name: "text", email: "text" });
};
```

### Reusable pure-field spreads

Shared validation objects keep models consistent. `createUpdateAt` gives every model the same timestamp fields:

```ts
export const createUpdateAt = {
  createdAt: optional(defaulted(date(), () => new Date())),
  updatedAt: optional(defaulted(date(), () => new Date())),
};
```

Used inside a model: `...createUpdateAt` at the end of `user_pure`.

### Shared relation excludes

Instead of repeating long `excludes` arrays, Satek centralizes them in `excludes.ts`:

```ts
export const user_excludes = ["createdAt", "updatedAt", "birth_date", "summary"];
export const ware_excludes = ["createdAt", "updatedAt", "price", "orderedNumber"];
```

A relation then just references its list:

```ts
organizations: {
  schemaName: "organization",
  type: "multiple",
  optional: true,
  excludes: organization_excludes,
  limit: 50,
  sort: { field: "_id", order: "desc" },
  relatedRelations: {
    users: { type: "multiple", limit: 50, sort: { field: "_id", order: "desc" } },
  },
},
```

### A rich relation graph: `purchasingRequest`

The purchasing request is the hub of the domain — 13 relations, each with its own excludes, limits, sorts, and back-references:


## The Action Layer

Each act is one folder with three files. The `mod.ts` describes the act to Lesan, the `.val.ts` builds the superstruct validator, and the `.fn.ts` implements the business logic.

### Describing an act: `mod.ts`

```ts
export const loginUserSetup = () =>
  coreApp.acts.setAct({
    schema: "user",
    actName: "login",
    fn: loginUserFn,
    validator: loginUserValidator(),
  });
```

Acts that mutate data run `validationRunType: "create"` (so `create` coerces defaults like `status: "Draft"`) and attach auth hooks through `preAct`:

```ts
export const addSetup = () =>
  coreApp.acts.setAct({
    schema: "purchasingRequest",
    fn: addFn,
    actName: "add",
    preAct: [setTokens, setUser, grantAccess([
      { roles: ["Manager", "Admin"] },
      { roles: ["OrgHead", "UnitHead", "Employee"], features: ["canRegisterPurchaseRequest"] },
    ])],
    validator: addValidator(),
    validationRunType: "create",
  });
```

### The validator: `.val.ts`

Validators compose shared pieces. `activeRoleMixin` and `pagination` come from `utils/`, `selectStruct` generates the client projection validator from the schema, and `objectIdValidation` validates MongoDB `_id` strings:

```ts
import { array, object, objectIdValidation, optional, string, number } from "@hemedani/lesan";
import { selectStruct } from "../../../mod.ts";

export const addValidator = () => {
  return object({
    set: object({
      ...activeRoleMixin,               // activeRoleId: string()
      title: string(),
      description: optional(string()),
      quantity: number(),
      wareModelId: objectIdValidation,
    }),
    get: selectStruct("purchasingRequest", 2),
  });
};
```

The pagination mixin is a tiny reusable superstruct object:

```ts
export const pagination = {
  page: optional(defaulted(number(), () => 1)),
  limit: optional(defaulted(number(), () => 50)),
  skip: optional(number()),
};
```

### The implementation: `.fn.ts`

Inside the act, `body.details` gives you `set` (validated input) and `get` (the client's projection). The first thing Satek does is pull the authenticated user out of the context and derive domain facts from the active role:

```ts
export const addFn: ActFn = async (body) => {
  const { set, get } = body.details;
  const { user }: MyContext = coreApp.contextFns.getContextModel() as MyContext;

  const { activeRoleId, wareModelId, title, description, quantity } = set;

  const activeRole = (user.roles || []).find((r) => r.roleId === activeRoleId);
  const requestingUnitId = activeRole?.scopeType === "unit" && activeRole?.scopeId
    ? activeRole.scopeId
    : undefined;

  if (!requestingUnitId) throwError("Your active role does not have an associated unit.");

  const result = await purchasingRequest.insertOne({
    doc: {
      title, description, quantity,
      status: "Draft",
      history: [{
        action: "created",
        performed: { by: user._id.toString(), name: `${user.first_name} ${user.last_name}`, at: new Date() },
        details: {},
      }],
    },
    relations: {
      requester: { _ids: user._id, relatedRelations: { requests: true } },
      wareModel: { _ids: new ObjectId(wareModelId as string), relatedRelations: { purchasingRequests: true } },
      requestingUnit: { _ids: new ObjectId(requestingUnitId), relatedRelations: { purchaseRequests: true } },
    },
    projection: get,
  });

  return result;
};
```

Note how relations are attached at insert time with `{ _ids, relatedRelations }` — the `relatedRelations` object declares which reverse snapshots to maintain (e.g. `user.requests` gets the new PR embedded).

## Authentication & Context

Satek threads the current user through the whole pipeline using Lesan's module-level context. It extends the base context type:

```ts
export interface MyContext extends LesanContenxt {
  user: { _id: ObjectId } & Partial<UserPure>;
}
```

### `setTokens` — verify the JWT header

The first `preAct` hook reads the `token` request header, verifies it, and stuffs the JWT payload into the context as `user`:

```ts
export const setTokens = async () => {
  const { Headers } = coreApp.contextFns.getContextModel();
  const token = Headers.get("token");

  if (!token) throwError("you should send your id with token key in req header");

  try {
    const verified = await jwt.verify(token, jwtTokenKey);
    coreApp.contextFns.setContext({ user: verified });
  } catch (_e) {
    throwError("Invalid or expired token");
  }
};
```

### `setUser` — load the real user

The JWT payload is stale by nature; `setUser` replaces it with the live document, loading the full pure projection plus `organizations` so later scoping logic can read the user's org:

```ts
export const setUser = async () => {
  const ctx = coreApp.contextFns.getContextModel() as MyContext;
  const tokenUser = ctx.user;

  if (!tokenUser || !tokenUser._id) throwError("Invalid or missing token data");

  const userPureProjection = coreApp.schemas.createProjection("user", "Pure");

  const foundedUser = await user.findOne({
    filters: { _id: new ObjectId(tokenUser._id) },
    projection: { ...userPureProjection, organizations: { _id: 1 } },
  });

  !foundedUser && throwError("user not exist");

  coreApp.contextFns.setContext({ user: foundedUser });
};
```

### `grantAccess` — role, feature, and scope checks

The reusable authorization hook takes an array of `RoleCheck`s. A user passes if any check matches their **active role** (chosen per-request via `activeRoleId` in the body). A check can require role(s), feature flag(s), and a scope function that must match the role's `scopeType`/`scopeId`:

```ts
export const grantAccess = (checks: RoleCheck[]) => {
  const checkAccess = () => {
    const { user }: MyContext = coreApp.contextFns.getContextModel() as MyContext;

    if (user.isGhost) return; // bootstrap superuser bypasses all checks

    const body = coreApp.contextFns.getContextModel() as any;
    const activeRoleId = body?.details?.set?.activeRoleId;
    if (!activeRoleId) return throwError("activeRoleId is required");

    const activeRole = user.roles?.find((r) => r.roleId === activeRoleId);
    if (!activeRole) return throwError("Active role not found");

    for (const check of checks) {
      if (!check.roles.includes(activeRole.name)) continue;

      if (check.features) {
        for (const feature of check.features) {
          if (!hasFeature(user, feature)) throwError(`Missing feature: ${feature}`);
        }
      }

      if (!check.getScope) return;

      const scope = check.getScope(body);
      if (scope && activeRole.scopeType === scope.scopeType && activeRole.scopeId === scope.scopeId) return;
    }

    throwError("You cant do this");
  };

  return checkAccess;
};
```

Feature checks are performed per user **and** per unit — a user inherits the features of the units they belong to:

```ts
export function hasFeature(user: UserWithFeatures, feature: Feature): boolean {
  if (user.features?.some((f) => f.feature === feature)) return true;
  if (user.units?.some((unit) => hasUnitFeature(unit, feature))) return true;
  return false;
}
```

### Scoping a list to the active role

Because `activeRoleId` is part of the validated input, a single `gets` act can serve completely different data depending on who calls it. Satek pushes role-specific `$match` stages into the pipeline:

```ts
const activeRole = (user.roles || []).find((r) => r.roleId === activeRoleId);

if (activeRole.name === "Employee" || activeRole.name === "Ordinary") {
  pipeline.push({ $match: { "requester._id": user._id } });
} else if (activeRole.name === "UnitHead") {
  if (activeRole.scopeType === "unit" && activeRole.scopeId) {
    pipeline.push({ $match: { "requestingUnit._id": new ObjectId(activeRole.scopeId) } });
  }
} else if (activeRole.name === "OrgHead") {
  if (activeRole.scopeType === "organization" && activeRole.scopeId) {
    pipeline.push({ $match: { "organization._id": new ObjectId(activeRole.scopeId) } });
  }
}
```

## Aggregation & Search

### Text search with relevance ranking

Satek's list endpoints accept `search`, `sortBy: "relevance"`, and `sortOrder`. When searching, it adds a text-score stage and sorts by it:

```ts
search && pipeline.push({ $match: { $text: { $search: search } } });

if (search && (!sortBy || sortBy === "relevance")) {
  pipeline.push({ $addFields: { textScore: { $meta: "textScore" } } });
}

const sortField = sortBy === "relevance" ? "textScore" : (sortBy || "_id");
const sortDirection = sortOrder === "asc" ? 1 : -1;
pipeline.push({ $sort: { [sortField]: sortDirection } });
```

### Cross-collection checks with `$lookup`

Filtering by the *existence* of a related record — e.g. "PRs that have no payment order yet" — is done with a `$lookup` and a `$size` match, keeping the check in one aggregation instead of a second query:

```ts
if (paymentOrderStatus) {
  pipeline.push({
    $lookup: {
      from: "paymentOrder",
      localField: "_id",
      foreignField: "purchasingRequest._id",
      as: "paymentOrders",
    },
  });
  if (paymentOrderStatus === "none") {
    pipeline.push({ $match: { paymentOrders: { $size: 0 } } });
  } else {
    pipeline.push({ $match: { "paymentOrders.status": paymentOrderStatus } });
  }
}
```

### Keyset-style pagination on a pipeline

Offset pagination composes with everything above as the final stages — skip/limit calculated from `page`, `limit`, and an optional explicit `skip`:

```ts
const calculatedSkip = skip ?? (limit || 50) * ((page || 1) - 1);
pipeline.push({ $skip: calculatedSkip });
pipeline.push({ $limit: limit || 50 });

return await purchasingRequest
  .aggregation({ pipeline, projection: get })
  .toArray();
```

### Count with the same filters

The matching `count` act rebuilds the same filter conditions and returns the document count, so the frontend can paginate:

```ts
const pipeline: Document[] = [];
// ... same role-scoped $match, $text, status stages as gets ...
pipeline.push({ $count: "total" });
const [result] = await purchasingRequest.aggregation({ pipeline }).toArray();
return result?.total ?? 0;
```

## Relations in Practice

### `addRelation` with `replace: true`

Satek never lets clients mutate relation arrays directly through update `$push` — a dedicated act manages relations and replaces the whole set with `addRelation({ replace: true })`:

```ts
export const updateUserRelationsFn: ActFn = async (body) => {
  const { set: { _id, avatar, organizations, state, city, units }, get } = body.details;
  const modelId = new ObjectId(_id as string);

  if (organizations) {
    await user.addRelation({
      filters: { _id: modelId },
      relations: {
        organizations: {
          _ids: (organizations as string[]).map((id) => new ObjectId(id)),
          relatedRelations: { users: true },
        },
      },
      projection: get,
      replace: true,
    });
  }
  // ...same pattern for avatar, state, city, units...

  return await user.findOne({ filters: { _id: modelId }, projection: get });
};
```

`replace: true` swaps the relation set to exactly the provided ids, and the embedded snapshot in the *target* documents is updated to match.

### Guarded deletion with `hardCascade`

Every `remove` act exposes an optional `hardCascade` boolean passed straight to `deleteOne`. By default deletion of a referenced document is blocked with the "please clear below relations status before deletion" error — Satek surfaces that to admins, who can force a cascade when they really mean it:

```ts
export const removeFn: ActFn = async (body) => {
  const { set: { _id, hardCascade }, get } = body.details;

  const result = await processStep.deleteOne({
    filter: { _id: new ObjectId(_id as string) },
    hardCascade: hardCascade || false,
  });

  // Satek then re-orders the remaining steps with aggregation + findOneAndUpdate...
  return result;
};
```

## Putting It Together

A request to `gets` the purchasing requests looks like this:

```bash
curl -X POST http://localhost:1370/lesan \
  -H "Content-Type: application/json" \
  -H "token: <jwt-from-login>" \
  -d '{
    "model": "purchasingRequest",
    "act": "gets",
    "details": {
      "set": { "activeRoleId": "uuid-1", "page": 1, "limit": 10, "search": "کیت TSH", "status": "InProgress" },
      "get": { "_id": 1, "title": 1, "status": 1, "estimatedAmount": 1, "requester": { "_id": 1, "first_name": 1, "last_name": 1 } }
    }
  }'
```

The pipeline to this point is what you saw in the [request lifecycle](/docs/advanced/request-lifecycle):

1. `setTokens` verifies the JWT header → context gets a `user`.
2. `setUser` replaces it with the live document + organizations.
3. `grantAccess` checks the active role's features (and scope, if any).
4. Superstruct `create` validation coerces defaults and validates the projection.
5. `getsFn` builds the role-scoped aggregation pipeline and returns `{ body, success: true }`.

Satek shows the patterns that make Lesan scale to a real domain: one act per endpoint, validators built from shared mixins, authorization as composable `preAct` hooks, rich relations with per-relation `excludes`/`limit`/`sort`, and aggregation pipelines that reuse the same filter logic across list and count endpoints.
