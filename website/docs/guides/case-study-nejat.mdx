# Case Study: NEJAT Road Accidents

**NEJAT** is a road-accident management and analytics system used for Iranian traffic data. With roughly **40 models** and a very data-heavy domain, it shows what Lesan looks like when the focus is less on CRUD and more on **spatial data, deep nested documents, and heavy aggregation analytics**.

## What Makes It Interesting

- **GeoJSON everywhere** — accident locations, roads, zones, and event areas are stored as real GeoJSON documents, validated by a hand-built superstruct type and queried with MongoDB's spatial operators.
- **Deep embedded documents** — an accident embeds `vehicle_dtos` (each with a driver, insurance data, damage sections, passengers) as plain superstruct arrays. No joins, no populate — the whole record comes back in one read.
- **Analytics as acts** — ~25 chart acts (`temporalCollisionAnalytics`, `spatialSeverityAnalytics`, `hourlyDayOfWeekAnalytics`, …) each run client-driven aggregation against the same `accident` model, so the dashboard picks which slice of data it wants per request.
- **Redis** — a shared `myRedis` connection is created at bootstrap and cached data is served from memory where it makes sense.

## Models & Relations

- **Geographic hierarchy:** `province → city → township`, `traffic_zone`, `city_zone`, `position`, `road`
- **Reference dictionaries:** `type`, `collision_type`, `road_situation`, `road_repair_type`, `shoulder_status`, `light_status`, `motion_direction`, `fault_status`, `ruling_type`, `area_usage`, `air_status`, `human_reason`, `vehicle_reason`, `equipment_damage`, `road_defect`, `road_surface_condition`, plus insurance/plaque/licence dictionaries
- **People:** `user`, `driver`, `person`, `event`, `event_process`, `police_station`
- **Core:** `accident` (with `seri`/`serial` numbering, `location`, `date_of_accident`, embedded `vehicle_dtos`/`pedestrian_dtos`)

The `accident` relations spread across the dictionaries — each one snapshots into the accident and the dictionary gets the reverse `accidents` back-reference:

```ts
export const accident_relations = {
  province:  { schemaName: "province",  type: "single", optional: true, relatedRelations: { accidents: true } },
  city:      { schemaName: "city",      type: "single", optional: true, relatedRelations: { accidents: true } },
  road:      { schemaName: "road",      type: "single", optional: true, relatedRelations: { accidents: true } },
  traffic_zone: { schemaName: "traffic_zone", type: "single", optional: true, relatedRelations: { accidents: true } },
  type:      { schemaName: "type",      type: "single", optional: true, relatedRelations: { accidents: true } },
  attachments: { schemaName: "file",    type: "multiple", optional: true },
  // ... 20+ more single and multiple relations
};
```

## Acts

Per-model `add` / `get` / `gets` / `count` / `update` / `remove`, plus two act folders that are the heart of the app:

- `accident/charts/` — one act per analytics dashboard widget
- `accident/maps/` — spatial queries returning GeoJSON-ready feature data

## Spatial validation with superstruct

NEJAT builds a reusable GeoJSON validator so every model that has a location shares the same strict type:

```ts
import { array, literal, number, object, tuple } from "@hemedani/lesan";

const Coordinate = tuple([number(), number()]);

const PointStruct = object({
  type: literal("Point"),
  coordinates: Coordinate,
});

const PolygonStruct = object({
  type: literal("Polygon"),
  coordinates: array(array(Coordinate)),
});
// ... MultiPoint, LineString, MultiPolygon, GeometryCollection
```

Used as a pure field on the model:

```ts
export const accident_pure = {
  serial: number(),
  location: geoJSONStruct("Point"),
  date_of_accident: date(),
  dead_count: number(),
  vehicle_dtos: array(object({
    color: common_relation_struct,
    driver: object({ /* ... */ }),
    insurance_co: common_relation_struct,
    motion_direction: common_relation_struct,
    // ...
  })),
  // ...
  ...createUpdateAt,
};
```

## Analytics acts: the same model, client-driven slices

A chart act takes the same `set` filters the client sends to `gets`, and returns exactly the aggregation the widget needs. This one issues three parallel `countDocument` calls — one per severity bucket — and lets the client decide date range:

```ts
export const accidentSeverityAnalyticsFn: ActFn = async (body) => {
  const { set: filters } = body.details;

  // Default date range: last full Jalali (Solar Hijri) year
  const now = moment();
  const lastJalaliYear = now.jYear() - 1;
  const startDate = moment(`${lastJalaliYear}/01/01`, "jYYYY/jMM/jDD").startOf("day").toDate();
  const endDate = moment(`${lastJalaliYear}/12/01`, "jYYYY/jMM/jDD").endOf("jMonth").endOf("day").toDate();

  const baseFilter = { date_of_accident: { $gte: startDate, $lte: endDate } };

  if (filters.seri !== undefined) baseFilter.seri = filters.seri;
  if (filters.deadCountMin !== undefined || filters.deadCountMax !== undefined) {
    baseFilter.dead_count = {};
    if (filters.deadCountMin !== undefined) baseFilter.dead_count.$gte = filters.deadCountMin;
    if (filters.deadCountMax !== undefined) baseFilter.dead_count.$lte = filters.deadCountMax;
  }
  // ... more filters, including $elemMatch into vehicle_dtos / pedestrian_dtos

  const [fatal, injury, damage] = await Promise.all([
    accident.countDocument({ filters: { ...baseFilter, severity: "Fatal" } }),
    accident.countDocument({ filters: { ...baseFilter, severity: "Injury" } }),
    accident.countDocument({ filters: { ...baseFilter, severity: "Damage" } }),
  ]);

  return [
    { name: "Fatal", count: fatal },
    { name: "Injury", count: injury },
    { name: "Damage", count: damage },
  ];
};
```

:::info Takeaway
NEJAT is the proof that Lesan scales to heavy analytical domains: the same `accident` model serves CRUD, spatial maps, and dozens of dashboard widgets — each one a normal act returning client-projected data with native MongoDB aggregation.
:::
